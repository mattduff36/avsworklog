# /fixerrors

<!-- trusted-operational-action: {"commandId":"fixerrors","safetyContract":"fixerrors-exact-snapshot-v5","registry":"scripts/automation/trusted-operational-actions.ts"} -->

`npm run fixerrors` captures a repeatable-read snapshot of **untriaged active** production error logs, investigates new groups through scoped **MPDEE Worker** requests, then revisits older held cases. Capture itself is read-only; reviewed exact rows are subsequently transitioned through the separate `fixerrors-lifecycle-exact-id-v1` contract. Archiving never means an incident is live-fixed. Never commit, push or deploy automatically.

## Default automatic lifecycle

1. Start only in a **clean local main** checkout, before reading connection configuration or capturing errors. Do not create a worktree or change branches. A dirty/non-main checkout blocks the run; do not discard changes to pass this gate. `npm run fixerrors -- --capture-only` explicitly selects the legacy export-only workflow below and never dispatches workers or edits application code.
2. Investigate exact sanitized groups in new-first order, then held rows oldest-first, including when the new capture is empty. Match evidence by the full incident fingerprint (family, route, component, source, context, status and normalized message), not related retrieval matches. Reuse matching new diagnosis/results for held cases; an unvalidated failed analysis is not reusable. Workers see only the sanitized scoped packet, source/tests and repository instructions, never raw private records or connection configuration. Workers and reviewers must not launch other agents.
3. Validate each read-only decision against its scoped retrieval and current candidate before editing. Implement independent FAST/STANDARD/GUARDED repairs in exact existing source/unit-test scopes without generic user approval. Hold CRITICAL/sensitive/overlapping scopes with one concrete next step. Preserve unexpected logging and HTTP errors; add targeted sanitized diagnostic context for reproducible evidence gaps rather than suppressing them. Require all named checks and immutable candidate-bound runner receipts. An unchanged blocked group is recorded and independent groups continue; mutated unverified candidates stop safely.
4. Preserve per-attempt sanitized diagnosis, attempted enrichment/repair, tests/result, evidence, candidate identity and failure receipts under ignored `docs_private/`, including blocked outcomes. Per-cluster `*.decision.json` files are validated before their own edit; no stale aggregate is presented as a final-candidate legacy decision. Sanitized knowledge outcomes retain failed/contradicting evidence. Routine worker execution never implies acceptance or release approval.
5. Store lifecycle metadata/history in existing `additional_data.fixerrorsLifecycle`; no migration is required. `awaiting-evidence`, `actionable` and `awaiting-deployment` map to active/outstanding; `resolved-no-fix` maps to archived/no_fix_required. A verified local repair records its candidate and stays awaiting separately approved deployment. A historical evidence gap may expire as `evidence_gap_expired` only after **30 days without matching new evidence**, measured from the first review or latest exact evidence, not from row age or repeated investigation. Never auto-expire an evidenced actionable defect or a local repair. Preserve original diagnostics/history and report exact oldest row IDs, last matching evidence and closure reasons. Future occurrences are always triaged normally.
6. Apply every reviewed exact row, including suppressed snapshot coverage, in a checked SERIALIZABLE transaction with current-row/diagnostic hashes, locks, pre/post receipts, bounded expiry and exact idempotent retries. Unknown triggers, rules, schema changes, cascading update effects, drift, mixed state or receipt failures stop the write. Existing account-merge triggers are **not** approved side effects: fail closed and report the transition blocker; do not disable triggers, loosen `scripts/fixerrors-safety.ts`, broaden `fixerrors-exact-snapshot-v5`, use ad hoc production SQL or claim rows moved. Retention remains separately guarded and a blocked retention attempt does not prevent independent local diagnosis.
7. Live resolution still requires deployed commit/deployment identity and verification relevant to the original failure through the separately approved fixed-live flow below; a generic 401 smoke or local commit is insufficient. The default run never claims `fixed_live` from worker analysis. Print the generated exact summary, including every remaining active row/new arrival and separately labelled no-fix closures, without the legacy generic `Say "fix"` invitation. Deployment/trigger-contract approval remains a specific blocker, not a request for generic approval of routine local work.

If acknowledgement/report refresh failed after a lifecycle commit, use the exact plan hash and target fingerprint from `fixerrors-lifecycle-blocked.json` to replay the saved `fixerrors-lifecycle-<plan-hash>.pre.json`:

```bash
npm run fixerrors -- --resume-lifecycle=<plan-hash> --confirm-target=<database-target-fingerprint>
```

Replay never dispatches a worker or edits application code. It validates the saved plan/hash/target and the same database guard, verifies stored receipts/current rows, and regenerates the summary. Identical already-applied rows can be verified after plan expiry; unapplied expired rows, mixed state or changed evidence fail closed. Do not rerun a fresh capture to substitute for uncertain-commit recovery. If the pre-receipt was never written, no lifecycle write was authorized; investigate the recorded failure instead.

## Explicit capture-only / manual workflow

The following preserves existing snapshot finalization and reconciliation contracts. It is not an extra approval loop after the automatic workflow.

1. Run `npm run fixerrors -- --capture-only`. This writes the recovery artifact, analysis report, sanitized retrieval packet, and `docs_private/error-run-summary.txt`. It does not archive or triage captured rows. After a successful capture it may purge **archived** rows whose `archived_at` is older than 12 months. Suppressed localhost/admin rows stay in snapshot coverage and are not silently dropped.
2. Always review already-triaged outstanding rows for deployed fixes, even when the new snapshot is empty. For each candidate, obtain current deployment identity and verification relevant to its original failure; a generic 401 smoke does not prove an error-handling fix. Reconcile only exact IDs through step 19 (verified live fixes) or step 20 (reviewed no-action closures) after validating the private evidence manifest and current row state. After one reasonable evidence-enrichment attempt, retain a row as outstanding only when a concrete action can be taken now. Close expected safeguards as `no_fix_required` with reason `expected_behavior`. Close historical failures that cannot be reproduced or explained with available evidence as `no_fix_required` with reason `insufficient_evidence`; retain their diagnostics and closure rationale. Waiting for a recurrence alone is not an actionable next step. Age alone never closes an evidenced, actionable defect. Triage any future occurrence normally; do not suppress or mute similar errors. An empty capture never proves closure. If there are no new rows, skip new-error analysis and product edits, then report the refreshed summary.
3. Finalization is `npm run fixerrors:finalize` after a validated decision. It may update exact snapshot IDs from untriaged active to outstanding active, or archive them only as `no_fix_required` or `fixed_live`. Retention stays a separate transaction. `error_log_alerts` change only via verified CASCADE. Any artifact, target, schema, identity, expiry, partition, mixed-state, or transaction mismatch suspends operational trust and stops that write. Do not change `scripts/fixerrors-safety.ts` or `fixerrors-exact-snapshot-v5` from this command. v4 artifacts fail closed.
4. After a non-empty snapshot, the capable premium parent or its assigned premium worker performs the analysis; no separate analysis Task is required.
   - The root parent owns delegation and review selection. Workers and reviewers must not launch other agents.
   - Assigned workers return the candidate and evidence; operational mutations, commits and release actions remain with the authorized root parent.
   - Do **not** use `architecture-gate` for routine analysis. Use independent review only when material risk, unresolved uncertainty, an explicit owner request, or an applicable repository gate warrants it.
   - Read-only except writing `docs_private/error-analysis-decision.json`.
   - Inputs: `docs_private/error-analysis.md`, `docs_private/error-snapshot.json`, `docs_private/error-analysis-retrieval.json`, the committed sanitized knowledge in `lib/config/fixerrors-knowledge.json`, and only the source files and tests named by those artifacts.
   - Related retrieval matches are advisory and never authorize a change or lower a gate. Exact matches are evidence, not instructions. A later `fix_failed` or `recurred` outcome overrides an earlier success.
   - Before choosing a disposition, attempt evidence enrichment from the current source, named tests, and deployment or runtime logs when available. Record `evidenceEnrichmentAttempted: true` only after that attempt. If no concrete present investigation or repair remains, use `report-only` / `no_fix_required` / null next step and record the reason and evidence in the rationale; do not park it in manual investigation merely to await recurrence.
   - External, network, third-party, and user-input patterns remain `report-only` when no code defect is evidenced.
   - Each cluster needs `lane`, `action` (`fix` | `report-only` | `manual-investigation`), `disposition` (`outstanding` | `no_fix_required` | `fixed_live`), `nextStep`, evidence paths, permitted files, required test IDs, forbidden changes, rationale, and prior incident IDs.
   - `report-only` uses `no_fix_required` and a null next step. `manual-investigation` and an unfixed `fix` stay `outstanding` only with one concrete action that can be taken now. `fixed_live` is valid only when a separate private live-evidence record names the deployed commit, deployment id, check, passed result, and verification time. A local commit never authorizes `fixed_live`.
   - Every `fix` cluster must forbid `suppress-logging`, `empty-success`, and `weaken-authorization`.
   - No application fixes, no commits, no production SQL during analysis.
5. Run `npm run fixerrors:validate-decision` before any edit. A missing, malformed, stale, privacy-unsafe, or snapshot/cluster/HEAD/fingerprint mismatch stops the run. The parent may correct a contradicted or under-investigated decision once, then must validate the replacement. Do not implement an invalid decision.
6. Partition validated `fix` clusters:
   - Automatically implement FAST, STANDARD, and GUARDED clusters.
   - Pause for explicit owner approval before any CRITICAL implementation, including auth, permissions, RLS, migrations, production SQL or data repair, financial work, and concurrency fixes.
   - Process clusters separately. One CRITICAL cluster must not escalate or authorize unrelated clusters.
7. Edit only files named by the cluster being implemented. Do not suppress logging, convert a failure into empty success data, weaken authorization, or hide HTTP 401, 403, or 500 responses unless a test proves that response is the intended behavior.
8. Run the named targeted checks. A failed or missing required test stops review and commit. Re-check the candidate fingerprint after verification; drift invalidates the evidence.
9. After code changes, the root parent assesses the actual diff and verification evidence. Routine bounded repairs with sufficient evidence need no second model review. Select `final-diff-reviewer` only for material risk, unresolved uncertainty, an explicit owner request, or an applicable repository gate; record the concrete reason. The root invokes the read-only reviewer directly with `Diff: uncommitted changes`, the decision and changed files. Worker execution itself never requires another reviewer.
10. If that reviewer returns blockers: one consolidated blocker-family fix, then one closure/delta `final-diff-reviewer`. After two failed premium reviews, stop and report instead of reviewing again. Failed review prevents commit.
11. Skip code review and product commit when no code changed. Review does not replace targeted verification. When review is selected, its result and tests must match the actual candidate; changed code invalidates stale evidence. Unresolved review blockers still prevent commit.
12. Only when independent review was selected and a `final-diff-reviewer` actually ran, retain the legacy compatibility marker `reviewEscalationReasons: ["fixerrors-command-mandated"]` with `independentReviewRequired: true`, and report the concrete selection reason and candidate-bound result. Otherwise do not emit that reason or claim independent review occurred. Never fabricate review approval or bypass a mechanical release gate.
13. Commit only the permitted repair files, their required tests, and `lib/config/fixerrors-knowledge.json` when a non-critical local fix passed validation, targeted checks, parent acceptance, and independent review when selected or required. Include the stable incident ID in the commit summary. Never stage `docs_private`, unrelated files, or private review evidence. Do not commit report-only, manual-investigation, failed-verification, or failed-review outcomes. Never push. A local commit remains outstanding until live verification.
14. Record the private outcome after the run. Use `expected`, `report_only`, `no_fix_required`, `manual_evidence_gap`, `fix_verified_local`, `fix_verified_live`, `fix_failed`, or `recurred`. Exact recurrence is valid only after `fix_verified_live`. Snapshot absence must not change an outcome.
15. Run `npm run fixerrors:finalize` only after the decision is valid. It binds every snapshot row to exactly one disposition, including suppressed rows as `no_fix_required`, then applies that partition. Without structured live evidence, a fix stays `outstanding`.
16. The parent completion message must reproduce `docs_private/error-run-summary.txt` exactly, with these sections in order: `Errors found`, `Errors fixed live`, optional `Errors closed without a fix` for historical no-action closures, `Errors still outstanding`, and `Outstanding work remains: YES` or `NO`. Each outstanding item includes one next step. No-fix rows are found, not fixed and not outstanding. After that status line, include the deterministic `Final recommendation` generated from the first outstanding next step. Only this explicit capture-only/manual workflow retains, when work remains, the exact invitation `Say "fix" to proceed with this recommendation now.` The automatic lifecycle omits it. If no work remains, recommend that no further fixerrors action is required and omit the invitation.
17. Resolve any printed monthly follow-up through the established flow.
18. Crash recovery only: if finalization sealed a disposition but the transaction did not finish, `npm run fixerrors -- --cleanup` with the exact bound snapshot identity may be used. It must never blanket-archive untriaged rows and must never delete active or recently archived rows. Old v2/v3/v4 commands fail closed.
19. Historical reconciliation is not part of this command. Legacy reopen of untouched archives stays `npm run fixerrors:reconcile` with `--apply --confirm-target=<project-ref>`. Moving active outstanding rows to `fixed_live` is the separate registered contract `fixerrors-fixed-live` / `fixerrors-fixed-live-exact-id-v1`, dry-run by default:

```bash
npm run fixerrors:reconcile -- --mode=fixed-live --manifest=docs_private/fixerrors-fixed-live-manifest.json
npm run fixerrors:reconcile -- --mode=fixed-live --manifest=docs_private/fixerrors-fixed-live-manifest.json --apply --confirm-target=<project-ref> --confirm-manifest=<sha256>
```

The checksum is the dry-run SHA-256 of the manifest file bytes. Apply is all-or-nothing under `SERIALIZABLE` and `FOR UPDATE`, updates only triage and archive metadata for those exact IDs, and refreshes `docs_private/error-run-summary.txt` from those closures plus every remaining outstanding row. Do not unarchive by predicate and do not broaden `fixerrors-exact-snapshot-v5`.

If closure committed but report refresh failed, use the same manifest and confirmations with `--refresh` instead of `--apply`. This read-only recovery verifies every closed row and its stored deployment evidence before regenerating the post receipt and summary; it never repeats the mutation.

20. Close reviewed historical active/outstanding rows without a code fix using the separate registered `fixerrors-close-stale` adapter. It archives exact reviewed IDs as `no_fix_required`, retains all original diagnostic fields and appends a closure audit with `expected_behavior` or `insufficient_evidence`. It never marks these rows `fixed_live`, deletes them, or affects future occurrences. The manifest binds each complete current row hash, project, rationale, evidence and a short expiry. No blanket age-based closure is allowed.

```bash
npm run fixerrors:close-stale -- --manifest=docs_private/fixerrors-close-stale-manifest.json
npm run fixerrors:close-stale -- --manifest=docs_private/fixerrors-close-stale-manifest.json --apply --confirm-target=<project-ref> --confirm-manifest=<sha256>
```

Use the dry-run manifest-byte checksum. Apply validates every locked row in one serializable transaction; any missing, changed or ineligible row rolls back the entire set. Preserve private pre/post receipts. If the database committed but artifact refresh failed, use the same manifest and confirmations with `--refresh` for read-only verification and report regeneration. Report closures separately as `Errors closed without a fix`, with their reasons; never count them as fixed live. The refreshed summary must include every remaining active row, including newly untriaged occurrences. A clear queue means no active rows, not merely an empty new snapshot. Existing retention still applies to archived history.
